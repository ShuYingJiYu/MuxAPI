# MuxAPI 设计文档

> AI API 多路复用调度转发网关
> 版本：Draft v0.1 ｜ 日期：2026-06-01

## 1. 背景与定位

### 1.1 要解决的问题

现有 sub2api 的账户调度存在结构性缺陷（已通过源码验证，sub2api v0.1.133+）：

| 缺陷 | 根因（代码佐证） |
|------|-----------------|
| **不回切（无 failback）** | 粘性会话 `sticky_session:{groupID}:{sessionHash}` 存 Redis，TTL 1h，账户挂了才清除并重绑到备用账户，高优先级账户恢复后不主动回切（`gateway_service.go:497-508`） |
| **优先级不严格** | 调度是加权随机 `score = w·priority + w·load + ...`，优先级只是一个因子，做不到「A 活着就必用 A」（`openai_account_scheduler.go:684-703`） |
| **故障发现被动** | 靠请求失败读 429 响应头 `reset_at` 才知道账户挂了，无主动健康探测；恢复也被动（`ratelimit_service.go:863-942`、`failover_loop.go:63-125`） |

**MuxAPI 要做的事**：提供一套严格优先级 + 主动健康探测 + 自动回切的调度，并保留向加权轮询、模型路由等策略生长的能力。

### 1.2 系统拓扑（关键架构决策）

```
用户 ──► sub2api ──► [仅 1 个 upstream 账户] ──► MuxAPI ──► 真上游 A/B/C
        (门面:计费/         (sub2api 调度被架空)    (调度大脑)    (均为中转平台)
         key/端点)
```

**决策要点**：
- sub2api 作为**面向用户的门面**：保留它的计费、API Key、用户体系、对外端点，用户无感。
- sub2api 后台**只配置一个 `upstream` 类型账户**，指向 MuxAPI。如此 sub2api 的加权随机/粘性/不回切因「只有一个出口」而被**架空**，痛点消失。
- **零改动 sub2api 代码**：仅在其管理后台加一个 upstream 账户即可。它升级不影响 MuxAPI。
- MuxAPI 是真正的**调度大脑**，其下游 A/B/C 均为**中转平台**（其他 sub2api / 兼容网关），MuxAPI 仅透传 key，**不做原生官方鉴权**（OAuth/Bedrock/Vertex 由那些上游自行处理）。

### 1.3 设计原则

- **完全兼容优先**：协议处理参考 sub2api 的 `apicompat` 思路，稳定与兼容性高于轻量。
- **可生长架构**：调度策略、上游类型、健康判定三者解耦，新增能力不改核心。
- **KISS**：MVP 先跑通核心场景，其余增量迭代。

## 2. 分层架构

```
            ┌──────────────────────────────────────────────┐
 sub2api ─► │ ① 接入层 Ingress                              │
 的请求     │   HTTP 入口 / 网关鉴权 / 解析 model+请求特征    │
 (OpenAI/   └───────────────────┬──────────────────────────┘
  Claude/                       ▼
  Gemini)   ┌──────────────────────────────────────────────┐
            │ ② 调度层 Scheduler ★核心★                     │
            │   可插拔策略链: 模型路由→严格优先级→加权→...   │
            │   入: 候选上游池 + 请求特征  出: 选中上游       │
            └───────────────────┬──────────────────────────┘
                                ▼
            ┌──────────────────────────────────────────────┐
            │ ③ 健康层 Health                               │
            │   主动真实探测(定时发最小token真实请求)        │
            │   + 熔断器(失败→OPEN→半开) + 被动反馈           │
            │   调度层只问它「谁现在能用」                    │
            └───────────────────┬──────────────────────────┘
                                ▼
            ┌──────────────────────────────────────────────┐
            │ ④ 转发层 Forwarder                            │
            │   按上游类型注入凭证 + 流式透传(SSE) + 重试    │
            │   失败结果反馈给健康层                          │
            └───────────────────┬──────────────────────────┘
                                ▼  真上游 A / B / C
```

### 三大解耦（决定项目上限）

1. **调度策略 ↔ 上游**：策略实现为接口链 `Strategy`，新增策略不动核心。用户提到「还没想到的功能」未来都是新增一个 Strategy。
2. **健康判定 ↔ 调度**：调度层永远只问健康层「谁能用」。**核心痛点回切由此自然实现**：健康层探测到 A 恢复 → 调度层（严格优先级）下次自然选回 A。
3. **上游类型 ↔ 转发**：原生(OAuth/key) vs 中转站(透传) 做成 `Upstream` 接口的不同实现，混合上游无痛。

### 核心痛点如何被解决

```
A 挂   → 健康层熔断 A → 调度层(严格优先级)发现 A 不可用 → 选 B
A 恢复 → 健康层主动探测到 A 活了 → 解除熔断
下个请求 → 调度层(严格优先级)发现 A 可用 → 立刻选回 A  ✅ failback
```

MuxAPI 默认**无状态、不做粘性**，每个请求都重走严格优先级，A 活着就必中 A，天然没有 sub2api 的「黏住」问题。

## 3. 调度策略链（Strategy Chain）

策略链按顺序过滤/排序候选上游池，每个策略输入候选列表输出候选列表：

```
候选池(全部健康上游)
  → [ModelRouteStrategy]   按请求 model 过滤出支持该模型的上游
  → [PriorityStrategy]     严格优先级排序(priority 小者优先)，只保留最高优先级层
  → [WeightStrategy]       同优先级层内按权重分流(可选)
  → 选中第一个
```

- **严格优先级**：与 sub2api 的加权随机相反——只要最高优先级层有健康上游，**必选该层**，绝不掺低优先级。同层多个才按权重/轮询。
- **可插拔**：每个 Strategy 是独立接口实现，配置决定启用哪些、顺序如何。这是「可生长」的落点。

## 4. 核心接口（Go 草案）

```go
// 调度策略：过滤/排序候选上游
type Strategy interface {
    Name() string
    Apply(req *Request, candidates []*Upstream) []*Upstream
}

// 上游：不同类型(原生/中转站)的统一抽象
type Upstream interface {
    ID() string
    Priority() int        // 越小越优先
    Weight() int          // 同优先级层内分流权重
    Supports(model string) bool
    // 构建发往上游的请求(注入凭证/baseURL/header)
    BuildRequest(req *Request) (*http.Request, error)
}

// 健康管理：调度层只依赖这个接口
type HealthManager interface {
    IsAvailable(upstreamID string) bool   // 调度层询问
    ReportResult(upstreamID string, ok bool, statusCode int) // 转发层反馈
    // 内部跑主动探测 + 熔断状态机(CLOSED/OPEN/HALF_OPEN)
}
```

## 5. 上游类型

**只做一种：中转透传（relay）**。MuxAPI 下游均为中转平台/sub2api 实例，原生官方鉴权(OAuth/Bedrock/Vertex)由那些上游自行处理，MuxAPI 专注转发+调度。

| type | 凭证结构 | 凭证注入 | 刷新 |
|------|---------|---------|------|
| `relay` | `{base_url, api_key}` | 双 header：`Authorization: Bearer {key}` + `x-api-key: {key}` | 否，静态透传 |

> 参考实现：sub2api `ForwardUpstream`(`antigravity_gateway_service.go:4263`)——读 `base_url`+`api_key`，拼 `base_url + 路径`，双 header 透传，透传上游错误码。
> 不做 token 刷新协程、不做 SigV4/Vertex 鉴权，**契合"纯转发网关"定位，符合 KISS**。
> 凭证 `api_key` 建议加密存储（密钥用环境变量）。

## 6. 数据模型（DB）

```
upstreams                          # 上游配置
  id, name, type(relay)
  priority(int,越小越优先), weight(int)
  api_key(加密), base_url
  enabled(bool), created_at, updated_at

upstream_models                    # 上游支持的模型(模型路由用)
  upstream_id, model_pattern(支持通配 claude-opus-*)

# 健康/熔断状态仅在内存(进程重启重新探测)，不落库
```

管理后台基于以上表做上游的增删改、优先级调整、启用/停用。

## 7. 协议兼容

参考 sub2api `internal/pkg/apicompat/` 思路：
- 入口路径：`/v1/messages`(Claude)、`/v1/chat/completions`(OpenAI)、`/v1/responses`(Codex)、`/v1beta/models/*`(Gemini)。
- **MVP 阶段优先做「同格式透传」**（同格式进同格式出，不转换），稳定且覆盖绝大多数场景。
- 流式 SSE 用 `bufio.Scanner` 逐事件透传。
- 跨格式协议转换（如 OpenAI 入 → Claude 上游）作为后续迭代，复用 apicompat 的链式转换思路。

## 8. 安全须知

- MuxAPI 入口需鉴权（sub2api 的 upstream key），**不可裸奔暴露**。
- 上游凭证加密存储（密钥用环境变量）。
- 管理后台需独立鉴权。

## 9. 前端管理后台

技术栈：**Vue3 + Vite**（与 sub2api 一致，便于参考其页面/组件）。

### 9.1 页面清单与路由

```
/login                 登录页(管理员鉴权)
/                      → 重定向到 /upstreams
/upstreams             上游管理(核心)：列表 + 增删改 + 优先级/权重 + 启停
/health                健康看板(核心)：实时熔断状态 / 探测结果 / 延迟
/logs                  调用日志与统计：usage / token / 成功率
/settings              系统设置：熔断阈值 / 探测间隔 / 策略链开关
```

### 9.2 组件树

```
App.vue
├─ LoginView.vue                       登录
└─ AdminLayout.vue                     主布局(侧边栏+顶栏)
   ├─ SideNav.vue                      侧边导航(上游/健康/日志/设置)
   ├─ UpstreamsView.vue                上游管理
   │  ├─ UpstreamTable.vue             列表(名称/优先级/权重/状态/启停)
   │  ├─ UpstreamFormDialog.vue        新增/编辑弹窗(base_url/api_key/优先级/权重)
   │  └─ PriorityDragSort.vue          拖拽调优先级(可选)
   ├─ HealthView.vue                   健康看板
   │  ├─ HealthCard.vue                每个上游一张卡(熔断态/延迟/最近探测)
   │  └─ CircuitBadge.vue              熔断状态徽标(CLOSED/OPEN/HALF_OPEN)
   ├─ LogsView.vue                     日志统计
   │  ├─ LogTable.vue                  调用明细
   │  └─ UsageChart.vue                token/成功率图表
   └─ SettingsView.vue                 系统设置(参数表单)
```

### 9.3 各页面字段

- **上游管理**：表格列=名称、base_url、优先级、权重、启用、熔断状态、操作(编辑/删除/启停)；表单=名称、base_url、api_key(加密)、priority、weight、enabled。
- **健康看板**：每上游卡片=名称、熔断状态徽标、最近探测时间、平均延迟、连续失败次数；可手动「立即探测」「强制恢复」。
- **日志统计**：时间、上游、model、状态码、token 用量、耗时；图表=各上游成功率/调用量。
- **系统设置**：连续失败熔断阈值、冷却时长、探测间隔、策略链顺序与开关。
